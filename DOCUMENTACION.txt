1. DESCRIPCIÓN GENERAL DEL PROYECTO
================================================================

El Sistema de Control de Acceso para Sala de Sistemas es una
aplicación web desarrollada en PHP que permite registrar y
controlar la entrada y salida de personas (estudiantes y
profesores) en una sala de cómputo institucional.

El sistema incluye:
  - Registro de entradas y salidas con timestamp automático.
  - Registro de la actividad que realizará la persona.
  - Distinción entre estudiante y profesor.
  - Panel administrativo completo con CRUD sobre toda la BD.
  - Reportes especiales con operaciones de álgebra relacional.
  - Procedimiento almacenado con validaciones de negocio.

3. BASE DE DATOS - ESTRUCTURA DE TABLAS
================================================================

3.1 TABLA: usuarios
-------------------------------------------------------------
Almacena la información de todas las personas que pueden
acceder a la sala (estudiantes y profesores).

COLUMNAS:
  - id_usuario            INT AUTO_INCREMENT
  - numero_identificacion VARCHAR(20)  — Cédula o código
  - nombre                VARCHAR(100)
  - apellido              VARCHAR(100)
  - tipo_usuario          ENUM('estudiante','profesor')
  - programa_facultad     VARCHAR(150) DEFAULT 'No especificado'
  - email                 VARCHAR(150)
  - telefono              VARCHAR(20)
  - estado                ENUM('activo','inactivo') DEFAULT 'activo'
  - fecha_registro        TIMESTAMP DEFAULT CURRENT_TIMESTAMP


3.2 TABLA: actividades_catalogo
-------------------------------------------------------------
Catálogo de actividades predefinidas que se pueden asignar
a un registro de acceso.

COLUMNAS:
  - id_actividad     INT AUTO_INCREMENT
  - nombre_actividad VARCHAR(150)
  - descripcion      TEXT
  - aplica_para      ENUM('estudiante','profesor','ambos')


3.3 TABLA: registros_acceso
-------------------------------------------------------------
Registra cada evento de entrada o salida de la sala.

COLUMNAS:
  - id_registro    INT AUTO_INCREMENT
  - id_usuario     INT (FK → usuarios.id_usuario)
  - id_actividad   INT (FK → actividades_catalogo.id_actividad)
  - tipo_movimiento ENUM('entrada','salida')
  - fecha_hora     TIMESTAMP DEFAULT CURRENT_TIMESTAMP
  - observaciones  TEXT
  - equipo_asignado VARCHAR(50)
  - registrado_por VARCHAR(100)


3.4 TABLA: administradores
-------------------------------------------------------------
Usuarios con acceso al panel de administración.

COLUMNAS:
  - id_admin       INT AUTO_INCREMENT
  - username       VARCHAR(50) UNIQUE
  - password_hash  VARCHAR(255) — Contraseña hasheada con bcrypt
  - nombre_completo VARCHAR(200)
  - email          VARCHAR(150)
  - ultimo_acceso  TIMESTAMP

4. RESTRICCIONES IMPLEMENTADAS EN LA BASE DE DATOS
================================================================

Se implementaron 5 restricciones de integridad, como se solicitó:

RESTRICCIÓN 1 — PRIMARY KEY
  Aplicada en: TODAS las tablas (id_usuario, id_actividad,
  id_registro, id_admin).
  Ejemplo: CONSTRAINT pk_usuarios PRIMARY KEY (id_usuario)
  Propósito: Garantizar unicidad e identificación de cada fila.

RESTRICCIÓN 2 — NOT NULL
  Aplicada en: numero_identificacion, nombre, apellido,
  tipo_usuario, id_usuario (FK), id_actividad (FK), tipo_movimiento,
  username, password_hash, nombre_completo, email (admins).
  Propósito: Evitar registros incompletos con campos vacíos.

RESTRICCIÓN 3 — UNIQUE
  Aplicada en: usuarios.numero_identificacion
  (CONSTRAINT uq_identificacion UNIQUE)
  y administradores.username (UNIQUE inline).
  Propósito: No puede existir dos personas con el mismo número
  de identificación, ni dos administradores con el mismo usuario.

RESTRICCIÓN 4 — CHECK (implícita vía ENUM)
  Aplicada en: tipo_usuario ENUM('estudiante','profesor'),
  tipo_movimiento ENUM('entrada','salida'),
  estado ENUM('activo','inactivo'),
  aplica_para ENUM('estudiante','profesor','ambos').
  Propósito: Solo se aceptan valores del dominio definido,
  equivalente semántico a un CHECK constraint.

RESTRICCIÓN 5 — DEFAULT
  Aplicada en: programa_facultad DEFAULT 'No especificado',
  estado DEFAULT 'activo', fecha_registro DEFAULT CURRENT_TIMESTAMP,
  registrado_por DEFAULT 'Sistema'.
  Propósito: Valores automáticos cuando no se especifica el campo.

RESTRICCIÓN ADICIONAL — FOREIGN KEY
  registros_acceso.id_usuario → usuarios.id_usuario
    ON DELETE RESTRICT ON UPDATE CASCADE
  registros_acceso.id_actividad → actividades_catalogo.id_actividad
    ON DELETE RESTRICT ON UPDATE CASCADE
  Propósito: Integridad referencial; no se puede registrar un
  acceso para un usuario o actividad inexistentes.

5. PROCEDIMIENTO ALMACENADO
================================================================

NOMBRE: sp_registrar_acceso

PARÁMETROS DE ENTRADA:
  p_id_usuario      INT      — ID del usuario
  p_id_actividad    INT      — ID de la actividad
  p_tipo_movimiento VARCHAR  — 'entrada' o 'salida'
  p_observaciones   TEXT     — Notas opcionales
  p_equipo          VARCHAR  — Equipo/PC asignado

PARÁMETRO DE SALIDA:
  p_resultado       VARCHAR  — Mensaje resultado de la operación

LÓGICA INTERNA:
  1. Verifica que el usuario exista en la tabla usuarios.
  2. Verifica que el usuario tenga estado = 'activo'.
  3. Verifica que la actividad aplique para el tipo de usuario
     (estudiante no puede registrar una actividad solo de profesor).
  4. Revisa el último movimiento del usuario para detectar
     inconsistencias (dos entradas seguidas, salida sin entrada).
  5. Inserta el registro en registros_acceso.
  6. Devuelve un mensaje con el resultado: OK, ADVERTENCIA o ERROR.

RETORNOS POSIBLES:
  "OK: Registro exitoso."
  "ADVERTENCIA: Se registra entrada aunque el último movimiento
   también fue entrada. Registro guardado."
  "ERROR: Usuario no encontrado en el sistema."
  "ERROR: El usuario se encuentra inactivo."
  "ERROR: La actividad no aplica para el tipo de usuario."

USO EN PHP (admin/registro.php):
  $stmt = $db->prepare("CALL sp_registrar_acceso(?,?,?,?,?,@p_resultado)");
  $stmt->execute([$idUsuario, $idActividad, $movimiento, $obs, $equipo]);
  $resultado = $db->query("SELECT @p_resultado AS res")->fetch()['res'];

6. CONSULTAS ESPECIALES — ÁLGEBRA RELACIONAL
================================================================

Todas visibles y ejecutables en: admin/reportes.php

-------------------------------------------------------------
A. UNIÓN (UNION)
-------------------------------------------------------------
OBJETIVO: Obtener todos los usuarios (de cualquier tipo) que
han registrado al menos un acceso, en un solo resultado.

SQL:
  SELECT nombre, apellido, 'Estudiante', programa_facultad,
         COUNT(*) AS total_accesos
  FROM usuarios JOIN registros_acceso ...
  WHERE tipo_usuario = 'estudiante'
  GROUP BY id_usuario

  UNION

  SELECT nombre, apellido, 'Profesor', programa_facultad,
         COUNT(*) AS total_accesos
  FROM usuarios JOIN registros_acceso ...
  WHERE tipo_usuario = 'profesor'
  GROUP BY id_usuario

  ORDER BY tipo_label, apellido

RESULTADO: Listado unificado de estudiantes y profesores activos
en la sala. El UNION elimina duplicados entre los dos conjuntos.


-------------------------------------------------------------
B. INTERSECCIÓN (simulada con IN doble)
-------------------------------------------------------------
OBJETIVO: Encontrar usuarios que poseen TANTO registros de
'entrada' COMO registros de 'salida' (ciclo completo).

MySQL no tiene INTERSECT nativo. Se simula así:

SQL:
  SELECT DISTINCT u.*
  FROM usuarios u
  WHERE u.id_usuario IN (
      SELECT id_usuario FROM registros_acceso
      WHERE tipo_movimiento = 'entrada'
  )
  AND u.id_usuario IN (
      SELECT id_usuario FROM registros_acceso
      WHERE tipo_movimiento = 'salida'
  )

EQUIVALENCIA: Esto es semánticamente idéntico a:
  {usuarios con entradas} ∩ {usuarios con salidas}

RESULTADO: Solo aparecen personas que están en AMBOS conjuntos.


-------------------------------------------------------------
C. DIFERENCIA (simulada con NOT IN)
-------------------------------------------------------------
OBJETIVO: Encontrar usuarios registrados en el sistema que
NUNCA han aparecido en ningún registro de acceso.

MySQL no tiene EXCEPT nativo. Se simula así:

SQL:
  SELECT u.*
  FROM usuarios u
  WHERE u.id_usuario NOT IN (
      SELECT DISTINCT id_usuario FROM registros_acceso
  )

EQUIVALENCIA: Esto es semánticamente idéntico a:
  {todos los usuarios} − {usuarios con algún acceso}

RESULTADO: Personas inscritas en el sistema pero que jamás han
entrado ni salido de la sala. Útil para detectar usuarios inactivos.

12. NOTAS ACADÉMICAS PARA SUSTENTACIÓN
================================================================

12.1 ¿Por qué simular INTERSECT y EXCEPT con IN / NOT IN?
  MySQL 5.x y 8.0 (hasta versiones recientes) no implementan
  las palabras clave INTERSECT y EXCEPT del estándar SQL:2003.
  La simulación con IN/NOT IN es completamente equivalente en
  resultado y es la práctica estándar en MySQL.

12.2 ¿Dónde está el UNION en el código?
  Archivo: admin/reportes.php, variable $unionQuery.
  El SQL se muestra visualmente en la interfaz para facilitar
  la sustentación.

12.3 ¿Dónde está el procedimiento almacenado?
  Archivo: database.sql — bloque DELIMITER $$
  Se invoca desde: admin/registro.php con PDO CALL.

12.4 ¿Dónde están las 5 restricciones?
  Todas en: database.sql, tabla usuarios (PRIMARY KEY, NOT NULL,
  UNIQUE, ENUM/CHECK, DEFAULT) y referenciadas en la sección 4
  de este documento.

12.5 Motor de tablas
  Todas las tablas usan ENGINE=InnoDB, que es el único motor
  de MySQL que soporta FOREIGN KEY y transacciones ACID.
